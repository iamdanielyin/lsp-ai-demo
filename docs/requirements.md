# 需求与交付范围

整理日期：2026-09-22。依据2026-09-18《LSP-AI客服Demo开发需求说明书》及后续对话变更。本文件是当前有效需求的整理，不代表真实租户验收通过。详细参数见 [参数手册](configuration-reference.md)，逐项验收状态见 [验收报告](acceptance-report.md)。

## 1. 目标

客户已经用 Freshdesk Omni 接通 WhatsApp、WeChat。Demo 作为外部 AI service，收到真实平台事件，读取同一会话历史，调用 OpenAI Responses API，向原会话及原渠道回复；必要时创建或复用 Freshdesk 跟进工单。

管理员使用一个设置页 `/settings` 和一个消息验证页 `/conversations`。除部署启动参数外，不要求编辑环境变量。代码可复用于后续项目第一阶段。

交付包括可运行源码、中文运行/配置/调度文档、占位 `.env.example`、数据库初始化方式、本地测试及真实验收模板。没有凭证也应完成实现和本地验证；真实项目只能标记 blocked / not_tested。

## 2. 最终确认的操作流程

1. 平台管理员确认实际接口路线，提供区域 API 地址、Freshchat Token、可回复的坐席、Webhook 公钥，并在平台订阅消息事件；部署人员提供 Demo 公网 HTTPS 回调地址。
2. Demo 管理员填写上述配置和 OpenAI Key。模型、预算、重试等预填默认值；OpenAI 请求地址可配置。
3. 在“测试账号与人工接管”选择 WhatsApp，主动点击“开启识别并自动回复”，生成5分钟有效的随机码。自己的 WhatsApp 账号向已接通客服账号发送该码。
4. Demo 对原始 Webhook 验签，匹配公开客户消息中的整段码，自动提取真实会话及客户 ID、绑定账号；读取历史并检查模型后生成第一条 AI 测试回复。无需手工查询两个 ID。
5. 再为 WeChat 生成新码，用自己的 WeChat 账号发送。两个渠道各保留一个测试账号，同时工作，分别保存历史、来源和控制状态。
6. 各渠道独立 AI／人工开关。关闭、Demo 手动回复或平台人工坐席参与会暂停该账号 AI；另一个渠道继续。恢复必须明确操作，只处理新消息。
7. 同渠道重绑替换旧账号，跨渠道新增保留另一个账号。“结束所有测试”撤销全部绑定、停用自动回复及待启动任务。在途请求不能撤回。

随机码是管理员主动开启的一次性授权凭据，不能公开或交给真实客户。昵称、手机号、微信号、固定 `LSP-DEMO-TEST-001` 都不能直接作为程序授权条件。已消费的码不能绑定第二个客户。

## 3. 原需求与后续调整

| 主题 | 原始要求 | 当前确认行为 |
| --- | --- | --- |
| 模型 | 填写有权限的模型，不假称最新 | 预填项目默认 `gpt-6-astra`，可修改，留空恢复；仍需真实账号检查，无自动追新 |
| OpenAI 地址 | 官方 API 为一期默认 | 管理员可填公网 HTTPS 基础地址或完整 `/responses`，需兼容 Responses 与严格结构化输出 |
| 首次获取 ID | 已知会话/客户 ID 手工导入 | 优先随机码自动识别；手动导入保留在折叠区 |
| 测试范围 | 单租户、按 ID 白名单 | WhatsApp 和 WeChat 各一个测试账号，身份/渠道绑定，不自动合并 |
| 开启自动回复 | 入站、历史、手动文本和 OpenAI 检查通过 | 随机码流程允许管理员主动授权的限定账号文本试运行；入站、历史、模型检查仍必要，手动文本三层验收不再阻塞启动，也不伪造通过状态 |
| 媒体自动回复 | 对应类型逐渠道验证后启用 | 保留。图片/视频/文件不能借文本试运行绕过验收 |

## 4. 平台路线与边界

当前只实现 **Freshchat 会话 API + Freshdesk 跟进工单**。必须确认真实新消息有 Freshchat `conversation_id`，区域 Token 能读取该会话和同一条消息，并能向该对象回复。

若租户新交互仅存在于新版 Omni Ticket，当前实现不适用：Ticket 事件、公开回复、structured_body、历史初始描述与后续30条分页等属于未实现路线；界面不提供伪开关。不能以成功创建 Freshdesk 跟进工单替代原渠道回复成功。Instagram 等连接器公共 API 限制也应单独核实。

Webhook 是消息到达平台后的异步通知，不是代理或前置拦截。平台原坐席/机器人继续运行，测试范围内需协调避免重复回复。全量订阅可能把全租户符合条件的事件请求发来；Demo 验签后忽略非测试客户，不保存正文、不拉历史、不调用 AI、不建单，但网络和验签成本仍存在。

不重新接入 Meta/微信；不替换 Omni 工作台；不建设完整工单系统；不调用全部停车交易接口。不得假称已预约、扣款、改车牌或完成真实交易。

## 6. AI 与素材约束

每次显式 `store:false`，不依赖 `previous_response_id`；不等于供应商日志零留存。模型接收按时间排序的客户可见历史、客服说明、获准知识和可用素材目录。内部备注、API凭证及其他客户资料不得进入上下文。收到媒体但没有文字时如实确认收到并请客户补充问题，不默认执行 OCR、视频理解、语音识别或附件解析。

结构化输出字段为 `messages[{type,text,asset_id}]`、`needs_human`、`ticket_reason`，不允许模型指定媒体 URL、目标会话或 Agent。媒体不生成新图/视频；只由后端发送管理员审核的确定版本。文件状态至少有待上传、扫描中、可发送、失败、停用；仅启用且可发送的素材进入目录。

完整历史同步与有限模型上下文分别显示。拒绝、incomplete、Token 超限、空输出、非法计划或请求失败必须停止本轮外发，不向客户转发供应商原始错误。需要人工时暂停；建单建议仅经规则、映射及去重后执行。

## 7. 可靠性与验收要求

每项任务持久化配置版本、触发消息、序号、次数、平台 ID、错误和时间。发送状态区分 queued/pending、generating、sending、accepted、delivered（仅有效回执）、failed、unknown、cancelled，部分后续任务可 paused。前一条已受理后不得因第二条失败重发；本地去重不宣称平台恰好一次。

能力矩阵逐渠道记录入站、历史、文本、图片、视频、文件、AI文本、AI媒体、工作台显示、Ticket、引用气泡。状态为 not_tested/passed/failed/blocked/unsupported。403优先记权限受阻，不能直接认定不支持。每个目标渠道需真实全闭环、至少10条自动回复和连续追问，记录实际耗时和用量，不承诺未经测试的响应速度或准确率。

T01–T17 的完整名称、状态和证据在 [验收报告](acceptance-report.md)，实际操作在 [测试手册](testing-guide.md)。原计划在账号、权限、公网、额度、渠道及素材齐备后约10–15工作日完成开发和验证；等待平台支持不算验证通过。

## 8. 当前未验证或未实现

- 真实 Freshchat/Omni 租户、WhatsApp、WeChat 连接器、OpenAI账号和自定义服务兼容性未实测。
- 新版 Omni Ticket 会话路线、机器送达回执、引用气泡、原生 Freshchat/Freshdesk 双向关联未实现。
- 视频原生接收、文件上传响应映射及扫描推进、渠道窗口和媒体限额须逐租户核实。
- 仅单管理员、单进程 worker；无高并发/多副本保障，未做客户全租户压力测试。
- 本地素材不做独立杀毒；文件魔数和 MIME 校验不等于安全扫描。真实业务知识/交易、附件内容理解不在一期范围。

上述限制不能通过本地替身测试或手工修改数据库标为通过。官方来源和历史核对日期见 [API依据](api-evidence.md)。
