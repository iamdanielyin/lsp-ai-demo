## 2. 后端自动化复现

完成依赖安装后在根目录运行：

```bash
.venv/bin/python -m unittest discover -s tests -v
node --check static/app.js
.venv/bin/python -m compileall -q lsp run.py scripts tests
```

Node检查可在有Node时执行，应用运行不依赖它。unittest使用临时目录、生成的RSA/Fernet密钥、Flask test_client，不读取 `.env` 的业务配置；连接真实供应商网络会被测试守卫拦截。

提交记录可用 `.venv/bin/python -m unittest discover -s tests -v > docs/local-test-results.txt 2>&1` 重建；同时更新报告和机器摘要中的真实日期、数量及耗时，不只修改通过数字。

关键回归覆盖：

- 设置加密/掩码/清除/默认迁移/自定义AI地址/版本失效/跨租户隔离。
- 原始body签名、篡改和缺签名；事务失败回滚；重复投递不重复任务。
- 100个其他客户用相同昵称/固定标记仍零入库、零历史和AI任务。这是功能测试，**不是全租户压力测试**。
- 多页历史、增量游标、同客户重开、私有备注隔离、媒体信息、未知来源。
- Responses输出遍历、refusal/incomplete/非法素材/条数/上下文预算/用量及预览不发送。
- 第二条外发失败不重发第一条，后续暂停；429、超时unknown、崩溃后不重发；人工在途状态。
- 建单映射、事项复用、规则、提交不明；调度缺配置/Token/参数/锁/opt-in/响应脱敏。
- 随机码权限/过期/替换/一次性、仅客户公开消息匹配、双渠道独立人工、来源交叉拒绝、新会话沿用暂停、更换一侧账号保留另一侧、启动中人工及结束、重启不重复启动。

## 3. 独立浏览器测试环境

两个夹具共用8128，**每次只启动一个**，与正常8127/8000实例隔离。

```bash
# 历史、图片/PDF界面、AI预览及工单
.venv/bin/python tests/browser_app.py
```

浏览器打开 `http://127.0.0.1:8128/settings`，用固定合成密码 `LOCAL-BROWSER-TEST-ONLY` 登录。123条初始历史可分页；文本+PDF发送后检查125条本地消息和两个独立任务；AI预览不外发；模拟Ticket #999；脚本文本以文字显示。这个实例所有供应商都是替身。

Ctrl+C停止后，可启动双渠道夹具：

```bash
.venv/bin/python tests/pairing_browser_app.py
```

同一地址/密码登录。界面先选择WhatsApp，点击“开启识别并自动回复”。夹具独有 `/api/local-test-message` 在管理员鉴权/CSRF后构造合成消息，再通过正常Webhook路由执行RSA验签。正常 `run.py` **不注册**该接口。

在此夹具页面的浏览器控制台执行以下合成测试操作；不要在正常实例或客户平台执行。真实测试推荐设置页的短时监听流程：

1. 选择 WhatsApp 或 WeChat，点击“监听下一批会话”。
2. 测试账号发送任意公开普通消息，等待候选出现。
3. 核对候选只含会话 ID、客户 ID、来源和时间，点选后打开消息页。
4. 等待历史同步完成，保持 AI 关闭；在单个会话右侧明确点击“恢复 AI”，再发送新问题。
5. 另一个渠道重复以上流程。未点选候选不会写入消息、事件或任务表。

旧兼容夹具控制台操作：

```javascript
const auth = await (await fetch('/api/auth')).json();
const state = await (await fetch('/api/test-discovery')).json();
const response = await fetch('/api/local-test-message', {
  method: 'POST',
  headers: {'Content-Type': 'application/json', 'X-CSRF-Token': auth.csrf},
  body: JSON.stringify({channel: state.enrollment.channel, text: state.enrollment.code})
});
console.log(response.status, await response.json());
```

控制台只查看HTTP状态/脱敏状态，不打印auth或完整设置。预期200/discovered；3秒轮询后出现WhatsApp的ID与AI开关。然后选WeChat、生成新码，重复该操作（重复执行时可刷新页面或用不同临时变量名）。

已执行的验证顺序：

1. 两个账号出现不同ID和独立开关，均为AI自动回复中，各收到一条合成模型测试问候任务。
2. 关闭WhatsApp开关，它转人工；WeChat仍auto。
3. 通过夹具接口给两者发送普通文本“本地合成追问：入口在哪里？”。WhatsApp受理发送数保持1，WeChat增长到2；未排队WhatsApp新AI。
4. 点击WeChat“打开会话，手动回复”，输入文本，预览目标后确认发送；WeChat转人工，文本在本地历史出现。
5. 恢复开关后先不发新消息，确认没有历史补回；再发新问题才生成。结束所有测试后，旧码/普通客户输入不能重新授权。
6. 检查每个关键HTTP响应体、控制台错误；直接调浏览器viewport为1440×1000及390×844并截图核对，页面无横向溢出。历史迭代还检查过799/801、1249/1251、519/521断点附近。

OpenAI地址页面回归：首屏可见默认地址；保存自定义基础/完整Responses地址后刷新保留；`https://127.0.0.1/v1` 返回400且不覆盖旧设置；留空恢复官方默认；密钥输入保存后仍空、显示已设置。后端测试另验证实际HTTP目标、store=false、strict schema、DNS与重定向拦截。

## 4. 真实客户环境准备

由平台管理员确认**当前新消息可用Freshchat会话API读取和回复**。如果只有新版Ticket接口，本实现停在blocked并记录证据。随后按 [平台配置指引](platform-setup.md) 准备Token/区域地址/专用Agent，配置公网回调、公钥；按 [参数手册](configuration-reference.md) 填OpenAI Key/模型/地址。

测试用自己的WhatsApp与WeChat，连接客户实际已接入账号。不使用昵称自动授权、不把码发给真实客户。协调关闭目标会话的其他机器人和重复自动回复。平台订阅有范围过滤则一并限制；否则要观察HTTP事件量，不能认为Demo的白名单消除了入口负载。

**准备顺序建议：** 先配置知识和审核素材及预计媒体主机，再开始识别。后续修改这些设置会关闭AI/使旧检查失效，需要重新检查与识别，避免把保存后的关闭误认为功能坏了。

## 5. 真实双渠道与人工介入步骤

| 步骤 | 操作 | 检查结果 |
| --- | --- | --- |
| 1 | 生成WhatsApp测试码，自己的账号发送 | 最近事件有正确消息ID；页面自动显示客户/会话/来源；历史同步真实完成 |
| 2 | 等待历史与OpenAI检查 | 成功后有模型请求ID、用量和第一条测试问候任务；失败明确显示，不强开 |
| 3 | 在Omni与手机核对问候 | API有消息ID、工作台发送者正确、原渠道设备实际收到，三层分别记录 |
| 4 | 生成WeChat新码，用自己的微信发送 | 第二个绑定产生；已绑定WhatsApp保留；新增绑定重新检查期间AI暂缓 |
| 5 | 双方分别发送不同停车场的追问 | 模型用各自历史，ID/来源/消息不串；不能以WhatsApp成功认定WeChat通过 |
| 6 | 关闭WhatsApp开关，两侧各发问题 | WhatsApp可见客户消息但不自动回复；WeChat继续AI |
| 7 | 在Demo给WhatsApp手动文本/媒体回复 | 预览目标正确，逐条任务受理；工作台与设备分别核实 |
| 8 | 恢复WhatsApp AI后等待，再发送新问题 | 恢复不会补发人工期间旧问题；新问题正常回复 |
| 9 | 在Omni由普通坐席回复WeChat | WeChat暂停AI；自身专用Agent的API回声不循环触发 |
| 10 | 生成期间追加客户消息/按人工开关 | 未发旧计划取消；已经提交项如实显示，不能声称撤回成功 |
| 11 | 关闭重开会话，保持同一真实客户ID | 沿用该渠道人工/自动状态；不同用户ID不自动合并 |
| 12 | 同渠道重新发新码换测试账号 | 旧账号不再外发，另一渠道绑定仍在；结束全部测试后两侧停止 |

测试码只在5分钟识别窗口有效；码若过期或平台延迟，重新生成再发送。当前未知来源必须带非空实际message_source才能映射，已知来源冲突会失败。页面没有事件不一定是没有网络请求：签名错误和非测试事件不在“已接纳事件”列表中，需结合部署者脱敏的HTTP状态检查，不能开日志记录全部客户正文来排查。

## 6. 历史、多条回复、媒体与工单

历史：测试会话准备超过50条可访问消息，确认完整分页、最早/最新时间、去重和关闭重开；客户前文说明停车场，后文问“那里的入口在哪里”，核对模型上下文范围及答案。上下文截断要展示，不能声称读了无限历史。

手动回复：一次准备两条独立文本，或文本+PDF，确认逐条任务和相同目标。模拟第二条明确失败时第一条不重发，第三条暂停；这种错误注入先用本地替身，真实生产渠道不随意造故障。

素材：准备获准停车位置图JPEG/PNG、停车指引MP4、方案PDF，填写清晰用途。先逐渠道手动上传/发送/接收/打开并记录三层证据；AV_PENDING不得当可发。视频必须是真实原生视频效果，发一个文字链接不能算通过。客户也分别上传媒体，核对历史类型、名称、大小；不测试未实现的OCR或视频理解。

真实AI分别提问：**发位置图、发停车指引视频、发方案PDF、文字解释方案、先说明再附PDF**。计划必须来自真实Responses输出，保留请求ID、计划、素材版本、用量和任务ID，不能用关键词硬编码伪造通过。首次媒体验收后若新绑定导致配置版本改变，需按当前矩阵重新核实媒体门槛。

工单：填写真实Freshdesk域名/Key、两侧Freshchat user ID到真实requester ID的映射、租户必填字段。手动创建，核对编号/链接/requester/摘要/来源；重复请求返回已有单，明确新事项才新建。当前不是Omni Ticket会话路线，不验证不存在的原生双向关联。

## 7. 失败、重启、调度与证据

本地先验证篡改签名、错误凭证、非法URL/文件/素材ID、角色过滤、429/超时、不明结果、重启恢复和CSRF。实际供应商错误需要有测试环境与证据，不能用本地通过代替。调度T17的curl、鉴权、dry-run、真实执行和错误码见 [调度手册](scheduler.md)。

每条外发分别保留：①API受理及消息ID；②原Omni时间线和正确Agent；③原客户设备收到及内容打开。人工确认记录测试人/时间/脱敏证据，不伪造机器delivered回执。

每渠道至少10条真实自动回复、至少一轮连续追问，记录每项入站到受理毫秒数、模型tokens和实际失败情况。使用 [tenant-evidence-template.json](tenant-evidence-template.json) 在受控位置填写；仓库内只保留占位或脱敏证据，禁止提交原始客户聊天/手机号/私密附件/Token。

状态规则：not_tested未执行，passed有具体证据，failed已执行失败，blocked缺权限/环境，unsupported有可靠平台限制依据。核心项未全部通过时，总体结论必须保持“核心能力未全部通过”。
