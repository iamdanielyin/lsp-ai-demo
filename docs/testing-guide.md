## 2. 后端自动化复现

完成依赖安装后在根目录运行：

```bash
.venv/bin/python -m unittest discover -s tests -v
node --check static/app.js
.venv/bin/python -m compileall -q lsp run.py scripts tests
```

Node检查可在有Node时执行，应用运行不依赖它。unittest使用临时目录、生成的RSA/Fernet密钥、Flask test_client，不读取 `.env` 的业务配置；连接真实供应商网络会被测试守卫拦截。

提交记录可用 `.venv/bin/python -m unittest discover -s tests -v > docs/local-test-results.txt 2>&1` 重建；同时更新报告和机器摘要中的真实日期、数量及耗时，不只修改通过数字。

关键回归覆盖：

- 设置加密/掩码/清除/默认迁移/自定义AI地址/版本失效/跨租户隔离。
- 原始body签名、篡改和缺签名；事务失败回滚；重复投递不重复任务。
- 兼容的显式白名单模式：100个范围外客户用相同昵称/固定标记仍零入库、零历史和AI任务。这是功能测试，**不是全租户压力测试**。
- 多页历史、增量游标、同客户重开、私有备注隔离、媒体信息、未知来源。
- Responses输出遍历、refusal/incomplete/非法素材/条数/上下文预算/用量及预览不发送。
- 第二条外发失败不重发第一条，后续暂停；429、超时unknown、崩溃后不重发；人工在途状态。
- 建单映射、事项复用、规则、提交不明；调度缺配置/Token/参数/锁/opt-in/响应脱敏。
- 兼容旧流程：随机码权限/过期/替换/一次性、仅客户公开消息匹配、双渠道独立人工、来源交叉拒绝、新会话沿用暂停、更换一侧账号保留另一侧、启动中人工及结束、重启不重复启动。

## 3. 独立浏览器测试环境

两个夹具共用8128，**每次只启动一个**，与正常8127/8000实例隔离。

```bash
# 历史、图片/PDF界面、AI预览及工单
.venv/bin/python tests/browser_app.py
```

浏览器打开 `http://127.0.0.1:8128/settings`，用固定合成密码 `LOCAL-BROWSER-TEST-ONLY` 登录。123条初始历史可分页；文本+PDF发送后检查125条本地消息和两个独立任务；AI预览不外发；模拟Ticket #999；脚本文本以文字显示。这个实例所有供应商都是替身。

Ctrl+C停止后，可启动双渠道夹具：

```bash
.venv/bin/python tests/pairing_browser_app.py
```

同一地址/密码登录。该夹具可用 `/api/local-test-message` 在管理员鉴权/CSRF后构造合成消息，再通过正常Webhook路由执行RSA验签；正常 `run.py` **不注册**该接口。

在此夹具页面的浏览器控制台执行以下合成测试操作；不要在正常实例或客户平台执行。真实测试推荐设置页的自动收集流程：

1. 在设置页保存 Freshchat 发送坐席。
2. 测试账号发送任意公开普通消息，等待新会话自动出现在 `/conversations`。
3. 打开会话，等待历史同步完成；默认 AI 关闭，右侧明确点击“恢复 AI”后再发送新问题。
4. 在“Webhook 最近事件”点击事件行查看原始 JSON。
5. 另一个渠道重复以上流程；不需要填写客户 ID 或会话 ID。

夹具中先保存坐席、点击“保存并检查 OpenAI”（只调用本地替身），再打开消息页。在浏览器控制台投递合成事件：

```js
await api('/api/local-test-message', {
  method: 'POST', body: {channel: 'WhatsApp', text: 'LOCAL_TEST：停车场入口在哪里？'}
});
```

等待3秒轮询显示会话，打开后应显示历史已同步、AI关闭。点击“恢复 AI”并确认，再发送下一条合成问题；检查任务包含独立模型用量、计划和平台受理ID。用 `channel: 'WeChat'` 再投递一个新会话，确认不会暂停 WhatsApp。人工接管只关闭当前会话；两个渠道的来源和历史不合并。“Webhook 最近事件”可查看合成原始载荷。

检查关键 HTTP 响应体和浏览器控制台；用真实 viewport 1440×1000、390×844 验证布局及无横向溢出。夹具仅验证应用行为，不证明渠道已接通。

OpenAI地址页面回归：首屏可见默认地址；保存自定义基础/完整Responses地址后刷新保留；`https://127.0.0.1/v1` 返回400且不覆盖旧设置；留空恢复官方默认；密钥输入保存后仍空、显示已设置。后端测试另验证实际HTTP目标、store=false、strict schema、DNS与重定向拦截。

## 4. 真实客户环境准备

由平台管理员确认**当前新消息可用Freshchat会话API读取和回复**。如果只有新版Ticket接口，本实现停在blocked并记录证据。随后按 [平台配置指引](platform-setup.md) 准备Token/区域地址/专用Agent，配置公网回调、公钥；按 [参数手册](configuration-reference.md) 填OpenAI Key/模型/地址。

测试用自己的WhatsApp与WeChat，连接客户实际已接入账号。不使用昵称自动授权，逐会话确认目标后开启 AI。协调关闭目标会话的其他机器人和重复自动回复。平台订阅有范围过滤则一并限制；否则要观察HTTP事件量，不能认为Demo的白名单消除了入口负载。

**准备顺序建议：** 先配置知识和审核素材及预计媒体主机，再接收新消息。后续修改这些设置会关闭AI/使旧检查失效，需要重新检查并在会话中恢复 AI，避免把保存后的关闭误认为功能坏了。

## 5. 真实双渠道与人工介入步骤

| 步骤 | 操作 | 检查结果 |
| --- | --- | --- |
| 1 | 保存发送坐席，用自己的 WhatsApp 发送普通消息 | 最近事件有正确消息ID；消息页自动显示客户/会话/来源；默认AI关闭 |
| 2 | 等待历史同步，检查OpenAI，在单会话恢复AI | 历史与模型检查通过；开启本身不补发历史 |
| 3 | 发一个新问题，在Omni与手机核对回复 | API消息ID、工作台发送者、原渠道收到三层分别记录 |
| 4 | 用自己的WeChat发送普通消息 | 第二个会话自动显示；WhatsApp模式和检查保持；WeChat默认AI关闭 |
| 5 | 为WeChat开启AI，双方分别追问不同停车场 | 模型用各自最近公开历史，身份/来源/消息不串 |
| 6 | WhatsApp人工接管后，两侧各发问题 | WhatsApp不自动回复；WeChat继续AI |
| 7 | 在Demo给WhatsApp手动文本/媒体回复 | 预览目标正确，逐条任务受理；工作台与设备分别核实 |
| 8 | 恢复WhatsApp AI后等待，再发送新问题 | 不补发人工期间旧问题；新问题正常回复 |
| 9 | 在Omni由普通坐席回复WeChat | WeChat暂停AI；自身API回声不循环触发 |
| 10 | 生成期间追加客户消息或点击人工接管 | 未发旧计划取消；已提交项如实显示 |
| 11 | 关闭重开或同一客户产生另一个会话 | 同一conversation_id保留状态；新的conversation_id默认关闭，不自动合并 |
| 12 | 设置页暂停收集并关闭AI | 所有会话未发送AI取消；新回调忽略；重新保存坐席可恢复收集 |

不需要固定字符串或手填ID。事件中没有坐席归属时，后台先读取会话详情；归属其他坐席时停止历史读取并移出列表。若平台始终不提供归属，页面会注明，管理员需核对目标后开启AI。未知来源只展示，在高级设置核实渠道映射后才发送。签名错误、范围外及非消息事件不会出现在“已接纳事件”列表，需结合脱敏HTTP状态排查，不记录全部客户正文到日志。

## 6. 历史、多条回复、媒体与工单

历史：测试会话准备超过50条可访问消息，确认完整分页、最早/最新时间、去重和关闭重开；客户前文说明停车场，后文问“那里的入口在哪里”，核对模型上下文范围及答案。上下文截断要展示，不能声称读了无限历史。

手动回复：一次准备两条独立文本，或文本+PDF，确认逐条任务和相同目标。模拟第二条明确失败时第一条不重发，第三条暂停；这种错误注入先用本地替身，真实生产渠道不随意造故障。

素材：准备获准停车位置图JPEG/PNG、停车指引MP4、方案PDF，填写清晰用途。先逐渠道手动上传/发送/接收/打开并记录三层证据；AV_PENDING不得当可发。视频必须是真实原生视频效果，发一个文字链接不能算通过。客户也分别上传媒体，核对历史类型、名称、大小；不测试未实现的OCR或视频理解。

真实AI分别提问：**发位置图、发停车指引视频、发方案PDF、文字解释方案、先说明再附PDF**。计划必须来自真实Responses输出，保留请求ID、计划、素材版本、用量和任务ID，不能用关键词硬编码伪造通过。手工修改业务配置后，需按当前矩阵重新核实媒体门槛；自动发现第二渠道不会使第一渠道检查失效。

工单：填写真实Freshdesk域名/Key、两侧Freshchat user ID到真实requester ID的映射、租户必填字段。手动创建，核对编号/链接/requester/摘要/来源；重复请求返回已有单，明确新事项才新建。当前不是Omni Ticket会话路线，不验证不存在的原生双向关联。

## 7. 失败、重启、调度与证据

本地先验证篡改签名、错误凭证、非法URL/文件/素材ID、角色过滤、429/超时、不明结果、重启恢复和CSRF。实际供应商错误需要有测试环境与证据，不能用本地通过代替。调度T17的curl、鉴权、dry-run、真实执行和错误码见 [调度手册](scheduler.md)。

每条外发分别保留：①API受理及消息ID；②原Omni时间线和正确Agent；③原客户设备收到及内容打开。人工确认记录测试人/时间/脱敏证据，不伪造机器delivered回执。

每渠道至少10条真实自动回复、至少一轮连续追问，记录每项入站到受理毫秒数、模型tokens和实际失败情况。使用 [tenant-evidence-template.json](tenant-evidence-template.json) 在受控位置填写；仓库内只保留占位或脱敏证据，禁止提交原始客户聊天/手机号/私密附件/Token。

状态规则：not_tested未执行，passed有具体证据，failed已执行失败，blocked缺权限/环境，unsupported有可靠平台限制依据。核心项未全部通过时，总体结论必须保持“核心能力未全部通过”。
